## 4. Documentation discrepancies requiring correction

### 4.1 Replication abort coverage

PR #264 and Issue #259 record the following evidence:
- One-shot `fetchindex` and follower read-back are verified on Solr 8.11.4, 9.11.0, and 10.1.0.
- In-progress abort/read-back is verified on Solr 9.11.0 and 10.1.0.
- Solr 8.11.4 is explicitly skipped/unverified for in-progress abort because repeated CI runs did not expose an observable active-fetch state.
- This is an evidence boundary, not a claim that Solr 8.11.4 does not support abort.

However, `docs/api-coverage.md` still describes abort and polling lifecycle behavior as unit-only. That statement is stale and should be updated to match PR #264 and `docs/compatibility.md`.

Polling claims should remain precise: do not imply that every polling mode or lifecycle variant is runtime-certified merely because bounded status polling is used by the abort test.

### 4.2 Collections backup/restore compatibility wording

The API coverage documentation describes core and SolrCloud backup/restore cycles as integration-tested on all three pinned Solr versions. The compatibility documentation also contains a broad residual statement that can be read as saying Collections snapshot/backup operations are unverified.

Reconcile the wording operation by operation. Preserve the tested evidence for the exact backup/restore flows, while retaining unverified status for any distinct snapshot, cluster-state, or action/response behavior that lacks direct evidence. Do not upgrade an entire API family to “tested” based on a narrower scenario.

### 4.3 Other explicit residual Update behavior

The current documentation identifies these narrower gaps:
- Delete-option `_route_` and `commitWithin` runtime effects.
- The optimize-specific runtime effect of `openSearcher`.
- Server-configuration-dependent hard/soft commit behavior for `commitWithin`.

The add/update routing and bounded `commitWithin` visibility tests do not establish delete-option behavior or an optimize-specific `openSearcher` effect. Keep these distinctions explicit.

### 4.4 Generic transport

`request()` and `requestRaw()` are transport escape hatches. Their generic transport behavior has unit coverage, but this does not certify arbitrary custom Solr endpoints. Keep endpoint-specific compatibility claims tied to endpoint-specific tests.

## 6. API coverage and compatibility boundaries

The project has substantial typed and runtime coverage. The following distinctions should remain explicit.

| Area | Current evidence or boundary |
| --- | --- |
| Query | Typed query options, response models, facets, highlighting, grouping, stats, MoreLikeThis, cursorMark, JSON facets, geospatial helpers; representative integration evidence on the pinned matrix |
| Update | CRUD, atomic updates, JSON update command variants and persisted-state assertions; add/update route and commitWithin evidence; delete-specific route/commitWithin remain unverified |
| Schema | Field, field type, dynamic field, copy-field operations and reads tested; plugin-specific similarity mutation remains type/serialization-only |
| Config | Typed commands and read models; isolated request-handler lifecycle and overlay read-back tested; plugin-specific component settings remain open |
| CoreAdmin | STATUS, CREATE, RELOAD and fixture-cleanup UNLOAD have integration evidence; several other actions remain type/serialization-only |
| Collections | Action-specific request/response contracts; evidence is action-specific. MODIFYCOLLECTION, SPLITSHARD, MIGRATE, ADDROLE and REMOVEROLE remain runtime-unverified pending the documented gates |
| Security | Authenticated/anonymous behavior and selected mutation/read-back tests on the pinned matrix |
| System | System information, properties, threads and logger metadata tested on the pinned matrix |
| Metrics | JSON/Prometheus response formats and node metrics group coverage; filters asserted where supported; plugin metrics remain open |
| Replication | One-shot leader/follower fetch and read-back on all three versions; in-progress abort on 9.11/10.1 only |
| Streaming Expressions | Complete JSON response parsing and SolrCloud search coverage; not an incremental tuple-stream parser |
| Export | Raw streaming coverage; `includeStoredFields=true` specifically verified on Solr 10.1.0 only |
| Raw transport | Generic transport tests do not imply endpoint-independent Solr compatibility |

The machine-readable `docs/api-inventory.json` should remain aligned with these operation-level claims. Do not claim blanket compatibility for an endpoint family when only selected actions or options have been exercised.

## 7. Deferred work and intentional non-goals

The current balanced scope does not require every possible Solr behavior to become a first-class typed feature.

Keep the following boundaries unless concrete consumer demand changes the priority:
- Version-specific error payload variants: defer until a concrete incompatible payload is identified.
- OAuth/mTLS credential lifecycle: deployment-specific; existing custom Fetch/header extension points remain available.
- Retry telemetry: caller observability concern unless a concrete shared contract is needed.
- Additional validation adapters/examples: add only for demonstrated ecosystem demand.
- Destructive/operational CoreAdmin actions: retain explicit unverified status until safe isolated tests are justified.
- Collections MODIFYCOLLECTION and cluster-wide role operations: defer unless safe deterministic verification is available.
- Plugin-specific Schema/Metrics/Auth contracts: intentional open extension boundary.
- Solr 10 V2 routes: separate API scope; do not silently treat V1 client methods as V2 support.
