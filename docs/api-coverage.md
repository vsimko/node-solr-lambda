# Solr API coverage

See the [public API reference](api-reference.md) for the package-root client methods and exported API groups. The documentation consistency check verifies the reference against the source declarations and package entry points.

See the [Solr endpoint inventory](endpoint-inventory.md) for the explicit typed-client boundary, deferred endpoint families, and official Solr reference sources.

The [Solr V2 API strategy](solr-v2-api-strategy.md) records the V1/V2 route map and version boundaries. The explicit `client.v2` namespace uses the shared transport and includes typed Core Admin, Collections lifecycle, cluster discovery, alias discovery, standard alias mutations, and alias property operations. Alias detail uses the documented GET route and falls back only on HTTP 405 to the V2 alias list; no V1 fallback is used. The new alias mutation/property methods have unit/type and isolated SolrCloud/BasicAuth fixtures, with runtime evidence pending on the pinned 9.11.0 and 10.1.0 baselines; Solr 8.11.4 is not claimed. Routed-alias creation and the remaining shard/replica operations (move, replica properties, split/force-leader) and backup/restore route families require separate request/response contracts and per-version runtime evidence. Typed addReplica() and exact deleteReplica() are now implemented with safe filesystem defaults, unit/type fixtures, and isolated topology/security tests; runtime evidence is pending on Solr 9.11.0/10.1.0, with Solr 8.11.4 unclaimed.

See [Client architecture](architecture.md) for module boundaries, type-model guidelines, and shared request conventions. The [roadmap](roadmap.md) tracks priorities and links to implementation issues.

See the [machine-readable API inventory](api-inventory.json) for each operation, request path, type coverage, unit-test status, and per-version integration status. The [Collections action coverage matrix](collections-api-coverage.md) maps each exposed Collections action to its input type, response contract, tests, and pinned Solr evidence.

The [testing and quality strategy](testing-strategy.md) defines the required evidence for each test layer, API-to-test traceability, failure-mode coverage, coverage reporting, and flaky-test policy.

A generic request method does not mean that every endpoint has a typed wrapper, useful IDE autocomplete, or tested version support. For supported features, the primary public API should expose named TypeScript properties and nested models that IDEs can complete and validate. Custom parameters remain available through an explicit escape hatch.

## Collections V2 backup and restore

The typed V2 backup surface now includes collection backup creation, backup-point listing and deletion, and restore (`v2.collections.backup()` and `v2.backups.*`). It uses the post-Solr-9.3 REST routes, not the V1 Collections parameter models. Solr 8.11.4 is explicitly unclaimed. Unit/type, isolated SolrCloud, and BasicAuth route-probe tests are present; runtime certification remains pending CI. See [Collections API coverage](collections-api-coverage.md) and [V2 strategy](solr-v2-api-strategy.md).

## Deferred work and explicit scope boundaries

The following gaps were reviewed for the TypeScript-first, balanced product scope. They are not implicit implementation commitments.

### Accepted, focused verification work

- **Export `includeStoredFields`** — verified on Solr 10.1.0 by [PR #261](https://github.com/vsimko/solr-ts-client/pull/261) using stored-only field read-back. Solr 8/9 behavior remains unclaimed.
- **ReplicationHandler abort/async lifecycle** — one-shot `fetchindex` and follower read-back are verified, but abort/polling semantics are not; tracked by [#259](https://github.com/vsimko/solr-ts-client/issues/259).

### Implemented feature/design work

- **RealTime Get (`/get`)** — implemented in [PR #271](https://github.com/vsimko/solr-ts-client/pull/271); the uncommitted single/multi-ID read-after-write integration test passed on pinned Solr 8.11.4/9.11.0/10.1.0 (CI run #42392182590).
- **SpellCheck** — implemented as an optional standard-query component in [PR #272](https://github.com/vsimko/solr-ts-client/pull/272); configured-handler integration coverage passed on all three pinned Solr versions (CI run #42392182590).
- **BigInt-safe JSON precision** — implemented in [PR #299](https://github.com/vsimko/solr-ts-client/pull/299) through an injectable `SolrJsonCodec`; native JSON remains the default, while callers can supply a lossless BigInt-aware codec.
- **Suggester** — implemented in [PR #298](https://github.com/vsimko/solr-ts-client/pull/298) as an optional query component; the disposable configured-handler integration test passed on pinned Solr 8.11.4/9.11.0/10.1.0 (CI run #42392182590).
- **Cross-client regression test audit** — completed in [PR #296](https://github.com/vsimko/solr-ts-client/pull/296); nested-document and Unicode read-back tests passed on all three pinned Solr versions in CI run #42392182590, while long-query and custom-handler behavior is covered by transport unit tests.
- **Streaming document ingestion** — implemented and merged in [#300](https://github.com/vsimko/solr-ts-client/pull/300), hardened in [#317](https://github.com/vsimko/solr-ts-client/pull/317), and completed with tests/docs in [#321](https://github.com/vsimko/solr-ts-client/pull/321) and [#325](https://github.com/vsimko/solr-ts-client/pull/325); 250-document count/order read-back passed on all three pinned Solr versions.
- **Prepare-commit lifecycle** — [#294](https://github.com/vsimko/solr-ts-client/issues/294) first audits existing typed update commands, then decides whether a dedicated method is justified.

### Deferred pending a concrete consumer requirement

- **Terms handler (`/terms`)** — deferred pending a concrete consumer requirement; this is distinct from Suggester and SpellCheck. Generic `request()` remains available.
- **Solr-version-specific error payload variants** — error envelopes preserve unknown fields and expose the typed common shape. Add version-specific models only when a concrete incompatible payload is identified and can be tested.
- **Advanced authentication (for example OAuth or mTLS)** — deployment-specific credential acquisition and certificate lifecycle are outside the built-in Basic/Bearer transport contract. The custom Fetch/headers extension points remain available.
- **Retry telemetry** — retry policy is opt-in; logging/metrics integration belongs to caller observability policy. The transport deliberately avoids logging credentials or server-controlled bodies.
- **Additional validation adapters and operation-specific schema examples** — the generic schema interface and optional Zod peer cover the supported extension contract. Add another adapter only for a demonstrated ecosystem demand.
- **Runtime verification of Core Admin `RENAME`, `SWAP`, `MERGEINDEXES`, `SPLIT`, `REQUESTSTATUS`, and `REQUESTRECOVERY`** — these operations have isolated/destructive or operational side effects and remain type/serialization-covered only until a safe, deterministic disposable environment is justified.
- **Collections `MODIFYCOLLECTION`, `ADDROLE`, and `REMOVEROLE` runtime verification** — these mutate cluster-wide policy/configuration and are not run against shared CI state. SPLITSHARD/MIGRATE have the separate opt-in gate in [#232](https://github.com/vsimko/solr-ts-client/issues/232).

### Intentional non-goals

- **Plugin-specific Schema similarity mutation and plugin-specific Metrics/Auth schemas** — arbitrary plugin contracts are not part of the closed typed surface. Common stable fields remain typed and extension points preserve unknown/custom fields.
- **Solr 10 V2 routes where the client explicitly implements V1 contracts** — V2 is a distinct API surface, not a silent compatibility extension. Add it only as a separately scoped feature with its own types and tests.

These decisions do not change the compatibility matrix: unverified operations remain unverified until exact runtime evidence exists.
 
## Request controls

Typed client methods support per-request cancellation and timeout controls. Caller cancellation throws `SolrAbortError`; a configured timeout throws `SolrTimeoutError`. The timeout remains active while JSON response bodies are read and while raw `requestRaw()` or export response streams are consumed. See [error handling](errors.md).

## Definition of done

An API feature is complete when it has:

1. Named, exported request and response types that provide useful IDE autocomplete.
2. Compile-time consumer examples, including typo/invalid-option checks where applicable.
3. Unit tests for serialization, request path, and response typing.
4. Documentation with realistic examples and version-specific notes.
5. Integration tests for each target Solr major version, or an explicit unverified/unsupported status.
6. A recorded compatibility result in [compatibility.md](compatibility.md).

Test every target endpoint against Solr 8.x, 9.x, and 10.x. Do not infer server support from a successful TypeScript build.


## Cross-client regression coverage

The cross-client audit identified and added focused coverage without broadening the public API:

- `add()` and `query()`: nested parent/child/grandchild document round-trip and exact Unicode/multi-valued field round-trip, in `test/integration/solr-document-fidelity.test.ts`.
- `query()`: long query parameter preservation on GET, without implicit GET-to-POST switching, in `test/transport-serialization.test.ts`.
- `request()`: custom handler path, repeated query parameters, and unknown/plugin-defined response fields in `test/raw-request.test.ts`.

The nested/Unicode integration tests are part of the normal standalone integration suite. Their source is added, but pinned Solr CI execution is still required before extending runtime compatibility evidence. Existing cursorMark, retry, cancellation, timeout, HTTP error, raw XML body, and SolrCloud shard-routing tests are retained rather than duplicated. See [ADR 0003](adr/0003-cross-client-test-strategy.md) and [issue #297](https://github.com/vsimko/solr-ts-client/issues/297).
